# 项目规格：多角色项目审批与执行工作流系统 (MAPA)

**项目代号**：MAPA
**目标**：从零构建一个纯Python桌面GUI应用，模拟企业级项目从提案到归档的全生命周期管理。
**核心哲学**：逻辑构成极度复杂，但技术栈极度克制（仅限Python标准库）。

---

## 1. 核心领域定义（数据模型）

你必须严格按照以下JSON Schema实现数据存储与内存对象。所有数据存储在 `~/.mapa/data.json` 中。

### 1.1 预算池 (BudgetPool)
```json
{
  "year": 2026,
  "total_budget": 5000000.00,
  "allocated": 0.00,   // 已执行/已验收项目的总金额
  "reserved": 0.00,    // 审批中项目锁定的金额
  "reservations": [    // 冻结明细
    {"project_id": "PRJ-XXX", "amount": 1000.00, "expires_at": "2026-07-30T17:00:00"}
  ]
}
```
*强一致性法则*：`available = total - allocated - reserved` 必须恒成立，任何写入操作必须校验此等式。

### 1.2 项目提案 (ProjectProposal)
```json
{
  "id": "PRJ-2026-001",
  "title": "string",
  "description": "string",
  "priority": 1,        // 1-紧急, 2-高, 3-中, 4-低
  "risk_level": "normal", // normal | high (触发敏感词自动标记)
  "channel": "standard",  // simple (<=50万) | standard (<=200万) | full (>200万)
  "budget_required": 850000.00,
  "proposed_start": "YYYY-MM-DD",
  "proposed_end": "YYYY-MM-DD",
  "status": "draft",    // 见状态机
  "current_node_id": "node_001",
  "reject_count": 0,    // 累计驳回次数
  "created_by": "user_alice",
  "submitted_at": null
}
```

### 1.3 审批节点 (ApprovalNode)
```json
{
  "id": "node_001",
  "project_id": "PRJ-2026-001",
  "node_type": "初审",   // 初审 | 会签 | 预算审批 | 法务合规 | 终审
  "required_role": "项目经理",
  "assigned_to": "user_bob",
  "status": "pending",   // pending | approved | rejected | escalated | timeout
  "deadline": "YYYY-MM-DDTHH:MM:SS",
  "escalated": false,
  "escalated_to": null
}
```

### 1.4 审批历史 (ApprovalHistory) —— 不可变日志
```json
{
  "id": "hist_001",
  "node_id": "node_001",
  "action": "reject",    // approve | reject | transfer | escalate
  "by": "user_bob",
  "at": "ISO8601",
  "comment": "string (>=20 chars on reject)",
  "is_final": false
}
```

### 1.5 里程碑 (Milestone) & 变更请求 (ChangeRequest)
*自行参照标准CRUD实现，必须包含状态字段和截止日期影响计算逻辑。*

## 2. 状态机定义（严格的流转逻辑）

项目状态 `status` 必须严格按照以下有向图流转，不允许跳跃：

`draft` → (提交) → `初审中` → (通过) → `会签中` → (通过) → `预算审批中` → (通过) → `待执行` → (启动) → `执行中` → (验收) → `已验收/已归档`

**异常分支**：
- 任意节点 `驳回` → **必须**跳转至 `修改中`。
- `修改中` → (重新提交) → 回到原驳回节点（重新开始该节点审批）。
- 若项目在 `修改中` 停留超过30天 → 自动变更为 `已搁置`。
- 若驳回次数 `reject_count` >= 3 → 状态强制变更为 `已搁置`，并通知高级管理员（仅UI提示）。

## 3. 十六大业务规则（必须全部硬编码）

| ID | 规则名称 | 逻辑详情 |
|----|----------|----------|
| **R1** | 预算阈值分流 | 提交时，`<=50万`→通道`simple`(需1人审批)，`>200万`→通道`full`(需增加外部专家节点) |
| **R2** | 角色完整性 | 项目成员中至少要有4种不同角色（如项目经理、技术负责人等），否则提交按钮置灰 |
| **R4** | SLA超时升级 | `pending`节点超过48小时未处理→状态变`escalated`，自动分配至上级角色（模拟） |
| **R5** | 预算硬锁 | 进入"审批中"状态瞬间，必须执行预算冻结（`reserved += budget`），失败则拒绝提交 |
| **R6** | 驳回必填理由 | 驳回操作时，输入框字符数必须 >= 10，否则无法提交 |
| **R7** | 一人一票 | 同一节点有多人时，其中**任一**人批准即通过（或签） |
| **R8** | 会签全票 | 节点类型为"法务合规"时，必须所有指定人批准才算通过 |
| **R9** | 变更影响追溯 | 任何`ChangeRequest`需对比新旧日期，若总延期>15天，必须额外走"延期审批"子流程 |
| **R10** | 不可回退 | 状态一旦进入`执行中`，严禁任何回滚操作，只能通过`ChangeRequest`修正 |
| **R11** | 紧急通道 | `priority=1`时，所有SLA时限减半（24小时），项目经理可一键跳过会签 |
| **R12** | 三次出局 | `reject_count >= 3` 自动搁置，需手动点击"解除搁置"才能重新激活（记录操作日志） |
| **R13** | 验收清单必填 | 进入`待执行`前，必须定义至少5项`验收标准`文本，否则无法启动 |
| **R14** | 预算执行率 | 归档时，实际录入支出与`budget_required`比值 <70% 或 >120%，必须弹窗强制填写偏离说明 |
| **R15** | 知识沉淀 | 归档时必须关联一份"经验总结"文档（仅存文本路径），否则归档按钮不可用 |
| **R16** | 冻结有效期 | 预算冻结(`reserved`)有效期30天，超期未转`allocated`则系统自动释放（模拟定时任务） |

## 4. 图形界面（GUI）强制布局规范

使用 `tkinter`。主窗口尺寸固定 `1400x900`。必须划分为 **5大面板**。

1.  **顶部工具栏** (`height=50`)：包含"新建项目"、"我的待办"、"全部项目"、"预算池仪表盘"、"报表"按钮。
2.  **左侧面板** (`width=250`)：**"我的工作台"**。
    - 展示待办清单（根据当前模拟用户过滤）。
    - 显示"我的审批统计"（通过率、平均耗时）。
3.  **中间面板** (自适应宽度)：**"项目列表/详情视图"**。
    - 默认展示卡片式项目列表（显示标题、优先级标签、当前阶段）。
    - 点击卡片后，切换为详情视图（展示所有字段、里程碑进度条）。
4.  **右侧面板** (`width=400`)：**"审批操作台"**。
    - 展示当前节点的审批人、截止倒计时。
    - 操作按钮：`[批准]` `[驳回]` `[转交]`。
    - 历史记录时间线组件（显示最近的5条`ApprovalHistory`）。
5.  **底部面板** (`height=100`)：**"预算池实时看板"**。
    - 必须包含 4个进度条/环形图，实时反映 `总预算/已分配/冻结/可用` 的动态变化。

## 5. 三大交互工作流（必须实现）

### 工作流 A：提交与分流
1. 点击"新建项目" → 弹出模态框。
2. 填写表单 → 点击提交 → 系统实时执行 `R1`(分流) 和 `R3`(敏感词检测)。
3. 确认提交 → **原子操作**：创建`Project` + 创建首个`ApprovalNode` + 执行`R5`(冻结预算) → 刷新所有面板。

### 工作流 B：审批处理
1. 左侧点击待办 → 中间显示项目详情，右侧加载当前节点。
2. 点击"批准" → 检查是否最后节点 → 若不是，创建下一个节点；若是，状态变更为`待执行`，`reserved`转`allocated`。
3. 点击"驳回" → 弹出输入框校验`R6` → 项目状态变`修改中`，`reject_count += 1`。

### 工作流 C：超时与异常
1. **后台线程**：启动一个`threading.Timer`，每60秒扫描所有`pending`节点。
2. 若 `当前时间 > deadline`，触发 `R4`：状态标记 `escalated`，并在界面顶部弹出红色警告横幅。

## 6. 用户角色与权限模拟

由于无后端登录，使用 `tkinter.OptionMenu` 在下拉栏切换用户（`alice(项目经理)`, `bob(财务)`, `carol(技术)`, `dave(法务)`）。
- **视图隔离**：左侧"待办清单"必须根据当前选中角色过滤（即只显示 `assigned_to` 匹配的节点）。
- **操作隔离**：非当前节点的 `assigned_to` 用户，右侧操作按钮必须置灰禁用。

## 7. 验收标准（AC）

你生成的项目必须能手动执行以下E2E测试，否则视为失败：

- **AC-1**：创建预算85万的项目，系统自动分配通道`standard`，提交后预算池冻结85万，可用金额减少。
- **AC-2**：`bob(财务)`登录，驳回该项目并输入少于20字的理由 → 系统拒绝驳回，提示字符数不足。
- **AC-3**：输入有效理由驳回 → 项目状态变`修改中`，`reject_count`显示1。
- **AC-4**：切换回`alice`修改后重新提交，节点回到财务处。
- **AC-5**：手动修改系统时间模拟超过48小时，后台线程自动升级节点（状态变`escalated`）。
- **AC-6**：`alice`将`priority`调为1（紧急），再次提交，SLA时限显示减半（24h）。

## 8. 技术红线（绝对不允许触碰）

- **禁止安装**任何第三方库（`pip install` 无效）。
- **禁止使用** `eval()` 执行动态代码。
- **禁止** 将数据仅存在内存中；退出程序再启动，必须能从 `~/.mapa/data.json` 完美恢复状态。
- **必须** 在数据变更时自动写入磁盘（`json.dump`），数据损坏时启动时自动尝试恢复 `data.json.bak`。
